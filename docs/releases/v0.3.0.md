# RSS-Zen v0.3.0 — Agent-operated Feishu daily digest

**Status:** in development  
**Schema version:** 6
**Upgrade source:** v0.2.0 / schema 4

## Objective

Reliably prepare and deliver topic-oriented Chinese news editions to a Feishu custom app bot before
an explicit `Asia/Shanghai` deadline, while keeping Pi Agent outside deterministic scheduling,
credentials, retries, idempotency, and delivery-state ownership.

See the [scope and acceptance plan](../plans/2026-08-14-v0.3-agent-feishu-digest.md) and
[ADR-0003](../adr/0003-agent-feishu-delivery-boundary.md).

## Implemented slices

### Schemas 5-6: topic, edition, and delivery persistence

Schema 5 introduces topic, edition, and delivery-outbox state required before Feishu network
integration:

- immutable, versioned `topic_profiles` with explicit timezone, delivery deadline, deterministic
  selection metadata, and safety limits;
- idempotent `edition_runs`, uniquely identified by topic-profile version and local edition date;
- a durable `delivery_outbox` with an idempotency key, artifact hash, bounded lease claims, retry
  state, terminal state, and confirmed provider message ID;
- atomic edition/outbox transitions so queued, delivering, delivered, and terminal states do not
  diverge across a process crash;
- repository validation that rejects invalid lifecycle transitions and sensitive metadata keys.

Schema 6 adds ordered `edition_run_items` that freeze selected article IDs and content provenance
without copying article bodies. It is a separate migration so databases initialized by the earlier
schema-5 development slice upgrade safely without redefining an applied migration.

This slice stores operational identifiers and aggregate counts only. Topic, edition-item, and
outbox fields do not store article bodies, Feishu credentials, authorization headers, or complete
provider responses. It does not call Feishu, invoke Pi, schedule editions, or implement generic
worker jobs.

### Deterministic edition builder

The offline edition builder now:

- applies a topic lookback window, source/category filters, keyword rules, deterministic ordering,
  title deduplication, dynamic candidate limits, and a rendered-byte ceiling;
- freezes selected article IDs and the chosen content provenance before rendering;
- prefers existing translated extraction, then translated RSS content, translated RSS summary,
  original RSS content, and original RSS summary, without initiating extraction or provider calls;
- renders normal, successful-empty, and translation-incomplete degraded Markdown editions;
- writes artifacts atomically, records a SHA-256 digest, and idempotently enqueues Feishu delivery;
- reconstructs a missing local artifact from frozen candidates and rejects target or hash drift on
  repeated execution.

The builder is a library slice only. Deadline scheduling and Pi editorial processing remain
unimplemented.

### Feishu outbound adapter and bounded worker

The outbound library slice now:

- obtains and refreshes a custom-app tenant access token in memory without persisting credentials;
- verifies the Markdown artifact SHA-256 before every attempt;
- uploads the Markdown file and sends a summary card plus file message to an opaque `chat:` target;
- derives stable per-message UUIDs from the outbox idempotency key so replay does not create a new
  logical card/file message;
- maps timeouts, network failures, HTTP 429, provider throttling codes, and 5xx responses to safe
  retryable errors while authorization, target, payload, and other request failures terminate;
- atomically persists retry, delivered, attempts-exhausted, and terminal states through the existing
  outbox lease contract;
- processes one bounded batch without sleeping, using persisted exponential retry timestamps.

All adapter tests use `httpx.MockTransport`. No production Feishu credential, target, network call,
CLI activation, timer, or inbound event handling is included in this slice.

### Configuration and local health contract

The additive configuration/observability slice now:

- adds inactive-by-default `[feishu]` settings for environment-variable names, an opaque `chat:`
  target, bounded worker limits, and `observe`/`warn`/`enforce` budget mode;
- resolves app ID and secret from the environment into excluded, non-repr fields; missing values do
  not prevent local `doctor` from reporting the exact missing environment-variable names;
- extends Health Contract v1 additively with aggregate edition and delivery counts, current budget
  mode, and latest delivered timestamp;
- reports pending/retrying work as a warning and terminal delivery as an error without contacting
  Feishu or exposing target IDs, credentials, article content, or provider responses;
- keeps example and deployment configuration disabled until a separately approved staging drill.

### Explicit CLI and default-disabled activation

The activation slice adds:

- `edition-build --dry-run --json`, which performs deterministic selection/render estimation without
  creating or migrating a database, writing an artifact, freezing candidates, or enqueueing work;
- explicit `edition-build`, which derives an `Asia/Shanghai` deadline (or validates normalized
  overrides), writes and hashes the edition, and enqueues it only when Feishu is enabled with an
  approved target;
- `delivery-run --dry-run --json`, which reads local outbox counts without claiming leases or
  contacting Feishu;
- explicit `delivery-run`, which refuses disabled or missing-credential configurations and processes
  exactly one bounded worker batch;
- hardened `rss-zen-delivery.service` and a persistent one-minute timer installed and verified by
  the deployment script but deliberately never enabled automatically.

All network-path CLI tests use `httpx.MockTransport`. Production activation still requires a
separately approved staging send.

### Versioned topics and deadline coordination

The coordinator slice adds:

- validated versioned `[[topics]]` for timezone, local deadline, preparation window, lookback,
  deterministic selection rules, and mandatory candidate/rendered-size ceilings;
- immutable topic reconciliation that rejects reusing a version with changed content;
- `deadline-run --dry-run --json`, which evaluates all enabled topic windows and previews selection
  without reconciling topics, creating editions, writing artifacts, or enqueueing work;
- explicit `deadline-run`, which opens at the configured preparation time, builds each local-date
  edition idempotently, and catches up for the current local date when invoked after the deadline;
- a network-denied deadline oneshot and an explicit `Asia/Shanghai` persistent one-minute timer that
  are installed and verified but never enabled automatically.

The coordinator does not refresh feeds, invoke translation/extraction providers, call Pi, or send
Feishu messages. Deadline and delivery timers remain separate failure domains.

## Upgrade and rollback

### Upgrade from schema 4

1. Stop `rss-zen.service` before deploying the schema-changing build.
2. Create and retain an operator backup of the database and production configuration.
3. Deploy the locked build and start the service.
4. Startup creates a verified WAL-aware snapshot under `backups/pre-migration/`, then applies
   outstanding schema migrations 5 and 6 in separate transactions.
5. Run `rss-zen doctor --json` and inspect `rss-zen status --json`; the reported database schema must
   be 6.
6. Before enabling Feishu delivery, run the edition/outbox backup-restore and replay drills described
   by the final release procedure.

Migrations 5 and 6 are additive and do not rewrite existing feed, article, translation,
extraction, export, or batch rows.

### Rollback

Code-only rollback from schema 6 to v0.2.0/schema 4 is **not supported**. Stop the service and restore
the matching verified pre-migration schema-4 snapshot before deploying v0.2.0. Do not point schema-4
code at a schema-6 database even though migrations 5 and 6 are additive.

## Remaining before release

- deterministic edition selection and fallback rendering;
- production Feishu permission/target review and an approved credential-injection drill;
- systemd activation plus an end-to-end staging outbox replay drill;
- explicit deadline coordinator and restart/catch-up behavior;
- cost observation and mandatory safety ceilings;
- Agent-safe feed/topic/edition operations and bounded Pi editorial integration;
- inbound Feishu authentication, deduplication, allowlists, and confirmation flows.
