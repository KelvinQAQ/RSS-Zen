# RSS-Zen v0.2.0 — Controlled operations

**Status:** planned

## Objective

Make manual extract/translate workflows predictable and observable on one Linux host while
preserving the current synchronous service architecture.

## In scope

### Batch budget and recovery

- Configuration limits for cumulative provider requests and source characters per command.
- Deterministic batch selection with `--limit`, `--dry-run`, JSON report output, and an
  operator-visible checkpoint that supports `--resume` after interruption.
- Per-run accounting of selected articles, source characters, requests, successes, failures,
  and skipped work.
- Clear terminal output when a budget prevents remaining selected articles from running.

### Operational contract

- Versioned `status --json` and `doctor --json` Health Contract v1 payloads.
- Both outputs provide `schema_version` and `generated_at`; additive fields are allowed within v1,
  while a breaking removal/rename/type change requires a new schema version.
- Feed freshness relative to configured poll interval; per-feed failure and last-success data.
- Database and WAL size, available disk capacity, backup directory size/freshness, batch summary,
  config ownership/mode checks, and conditional curl prerequisite checks.
- `doctor` exits 0 for ok/warning checks and 1 for any error, without contacting feeds/providers.
- An optional hourly systemd health-check timer records doctor errors in journald but never restarts
  the service.

### Retention lifecycle

- Configured article, failed-extraction, and export-run retention settings.
- `retention --dry-run` before destructive actions and `retention apply` for explicit cleanup.
- Retention is disabled unless `[retention]` explicitly configures a positive UTC-day period;
  running/interrupted batches are never candidates.
- Verified backup before deletion; report deleted records and backup path.
- Explicit `maintenance checkpoint` and opt-in `maintenance vacuum`; vacuum checks local free disk
  capacity and should run only in an approved maintenance window.

### Deployment

- Optional systemd health-check timer that records failures in journald.
- Documentation for consuming JSON health output with existing alerting systems.

## Out of scope

- SQLite jobs table or asynchronous workers.
- Automatic AnySearch extraction.
- Multiple service hosts, Redis/Celery, PostgreSQL, or web API.
- Provider-specific token billing calculations; budgets are based on request and source-character
  counts only.

## Delivery slices

1. **Budget accounting:** model/config validation, shared budget object, reports, and tests.
2. **Batch checkpoints:** persisted run/checkpoint record, resume CLI semantics, recovery tests.
3. **Health contract:** stable JSON schema, repository metrics, filesystem checks, tests.
4. **Retention:** preview/apply commands, migration if required, backup/restore tests.
5. **Operations:** systemd timer, documentation, release verification.

Each slice must be independently mergeable and must not require a schema migration unless its
release notes, pre-migration backup test, and rollback consequences are included.

## Exit criteria

- A dry run exactly reports the selected work without external provider calls.
- Every bounded run reports selected/completed/skipped/failed article counts, request count, and
  source-character count in a machine-readable form.
- Interrupted runs resume without reprocessing successful work.
- `doctor --json` accurately reports stale feeds, backup health, database/WAL/disk status, and
  exits nonzero for unhealthy conditions.
- Retention does not delete data without an explicit apply command and a verified backup.
- Full test suite, lint, dependency audit, and BOM checks pass.
