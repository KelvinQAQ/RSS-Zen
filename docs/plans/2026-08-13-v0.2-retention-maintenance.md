# v0.2 Slice 4: Explicit Retention and SQLite Maintenance

**Status:** In progress
**Target version:** v0.2.0
**Task:** local-only tracking `t-005`

## Goal

Control local SQLite growth without automatic deletion. Operators preview candidates first, then
explicitly apply retention after a verified SQLite backup. Maintenance operations are separate from
retention and never run automatically.

## Configuration

Retention is disabled unless the optional `[retention]` table is configured:

```toml
[retention]
articles_days = 365
failed_extractions_days = 30
export_runs_days = 90
batch_runs_days = 30
```

Every configured value is a positive number of UTC calendar days. Omitting a field disables that
category. There are no default deletion periods.

## Commands

```bash
rss-zen retention --dry-run --config rss-zen.toml
rss-zen retention apply --config rss-zen.toml
rss-zen maintenance checkpoint --config rss-zen.toml
rss-zen maintenance vacuum --config rss-zen.toml
```

### Retention

- `--dry-run` only counts candidates; it does not create a backup, delete data, checkpoint, or
  vacuum.
- `apply` is the only destructive action. It creates a verified backup with the configured backup
  policy before deletion.
- Deletion happens in one SQLite transaction. If backup fails, no deletion runs.
- Article deletion cascades translations, extractions, and checkpoint items through existing foreign
  keys. Only articles whose `last_seen_at` is before the UTC cutoff qualify.
- Failed extractions are deleted only when their `created_at` is before the cutoff; successful
  extraction history remains.
- Export runs and completed batch runs are deleted only when their timestamps precede the cutoff.
  Running/interrupted batches are never removed by retention.

### Maintenance

- `checkpoint` performs `PRAGMA wal_checkpoint(TRUNCATE)` and reports its result.
- `vacuum` is opt-in and first requires free disk space at least the current main database size.
  It may block writers, so run only while the service is stopped or in an approved maintenance
  window.
- Neither maintenance command makes external network calls or deletes article data.

## Output and audit

All commands support existing human output. `retention --dry-run` and `retention apply` return
structured counts for article, failed extraction, export run, and completed batch-run candidates.
The apply command reports the verified backup path. The CLI never logs article content or provider
responses.

## Out of scope

- Automatic retention timer; production operators must schedule `apply` deliberately after a
  successful dry-run period.
- Per-feed retention policies, archive-to-object-storage, compression, or database sharding.
- Automatic vacuum/checkpoint from `serve`.

## Acceptance criteria

- No data is deleted with retention absent or during dry-run.
- Apply creates verified backup before a single transactional delete.
- Running/interrupted batch runs are retained.
- Config validation, selection counts, apply, backup failure, WAL checkpoint, and vacuum free-space
  checks have deterministic tests.
- Full quality gates pass and deployment/release documentation explains operational constraints.
