# v0.3: Agent-operated Feishu Daily Digest

**Status:** Proposed scope  
**Target version:** v0.3.0  
**Local tracking:** milestone `m-003`, task `t-008`  
**Timezone:** `Asia/Shanghai`

## Problem statement

RSS-Zen should operate as a stable capability behind Pi Agent rather than as a CLI that requires
routine human operation. Before a configurable daily deadline, it must deliver a Chinese news
edition for each enabled topic to Feishu. An edition must remain useful when individual feeds,
translation providers, Pi editorial processing, or Feishu temporarily fail.

The system remains single-host and SQLite-based. Pi interprets user intent and performs bounded
editorial work, while RSS-Zen owns deterministic scheduling, durable state, budgets, retries,
idempotency, fallback generation, and delivery evidence.

## Approved product decisions

1. The first delivery channel is a **Feishu custom app bot**, not a group webhook.
2. The number of selected articles is dynamic. Relevance, source diversity, duplicate-event
   suppression, content length, and safety ceilings determine the final count.
3. Prefer already-stored extracted full text, then RSS-provided content, then RSS summary. Daily
   delivery never waits for automatic full-text extraction. Explicit Agent-requested extraction
   remains supported.
4. Provider and Agent cost controls are designed now. Initial production operation uses an
   observation mode; concrete daily/monthly financial limits are set after measured usage.
5. `07:30 Asia/Shanghai` is a delivery deadline, not the start time for ingestion.

## Product journeys

### Scheduled daily delivery

1. RSS-Zen continuously ingests enabled feeds according to their effective polling intervals.
2. A deadline coordinator opens one `edition_run` per enabled topic before its deadline.
3. Priority feeds receive a bounded final refresh.
4. Deterministic rules select, deduplicate, and rank candidates.
5. Required candidate fields are translated within provider and deadline budgets.
6. Candidate selection freezes before editorial processing.
7. Pi receives a bounded, content-minimized editorial input and returns a versioned structured
   edition, not an unrestricted delivery command.
8. RSS-Zen renders a deterministic Markdown artifact and Feishu summary card.
9. A durable outbox sends the edition idempotently and records delivery evidence.
10. If Pi or a provider misses its cutoff, RSS-Zen sends a deterministic degraded edition before
    the final deadline.

A successful empty edition is valid. It must state that no qualifying updates were found so the
recipient can distinguish an empty news day from a pipeline failure.

### Add a public feed through Pi

1. The user asks Pi to monitor a URL under a named topic.
2. Pi calls an allowlisted `feed probe` operation.
3. RSS-Zen validates URL policy and redirects, detects duplicates, verifies RSS/Atom content, and
   returns a safe sample summary without returning article bodies or credentials.
4. For a public HTTPS feed that passes policy, Pi calls `feed add` and reports the result.
5. Private headers, authentication, unexpected redirects, or policy warnings require explicit
   confirmation and a separately managed credential reference.
6. RSS-Zen performs a bounded first synchronization and records health evidence.

### Request full text through Pi

The user may explicitly request extraction for selected article IDs. Pi invokes a bounded
extraction operation, reports partial failures, and can subsequently build a topical report. This
workflow does not alter or block the daily edition deadline.

## System boundary

### RSS-Zen owns

- feed polling, conditional requests, retry scheduling, and feed health;
- article persistence, translation state, content provenance, and deduplication inputs;
- topic definitions and deterministic candidate selection;
- edition/deadline state machines and fallback rendering;
- provider, Agent, and delivery usage accounting;
- delivery outbox, Feishu retries, idempotency, and delivery receipts;
- stable JSON contracts and an audit trail for Agent-requested mutations.

### Pi Agent owns

- natural-language interpretation;
- bounded editorial ordering, grouping, introductions, and Chinese copy editing;
- presenting proposed feed/topic changes and requesting confirmation when policy requires it;
- invoking only allowlisted RSS-Zen operations through typed tools.

### Pi must not own

- wall-clock scheduling or retry loops;
- raw SQLite access;
- arbitrary production shell or filesystem access;
- Feishu credentials or provider secrets in prompts/session content;
- direct message delivery that bypasses the outbox;
- destructive retention, database restore, or budget increases without explicit confirmation.

## Deadline model

A topic config stores a timezone and delivery deadline. A representative schedule for a 07:30
edition is:

| Time (`Asia/Shanghai`) | Phase |
|---|---|
| Continuous | Normal feed polling and translation work. |
| 06:30 | Create the daily edition run. |
| 06:35 | Submit bounded final-refresh jobs for priority feeds. |
| 06:45 | Select, deduplicate, rank, and balance sources. |
| 07:05 | Freeze candidates; late articles move to the next edition unless explicitly retried. |
| 07:05-07:18 | Pi editorial pass within a hard input/output and time budget. |
| 07:18 | Render and enqueue delivery. |
| 07:18-07:28 | Retry transient Feishu failures with bounded backoff. |
| 07:30 | Deadline: deterministic fallback must already have been attempted. |

Per-topic times are configurable. Tests use an injected clock and do not rely on host local time.
Systemd timers use explicit `Asia/Shanghai` calendar expressions and `Persistent=true`, but systemd
only wakes the coordinator; durable database state decides what remains to run.

## Topic and content semantics

A versioned topic profile contains at least:

- stable ID and display name;
- timezone, deadline, lookback window, and enabled state;
- multilingual keywords, entity aliases, negative terms, and optional preferred feeds;
- relevance floor, source-diversity rules, duplicate-event policy, and safety ceilings;
- language/output settings and a versioned editorial instruction;
- Feishu target reference and budget policy reference.

The selected article count is not fixed. The implementation must nevertheless enforce configurable
safety ceilings for candidate count, per-source contribution, rendered bytes, translation input,
and Pi context. A topic with no qualifying article produces a successful empty edition.

Content provenance is explicit:

```text
extracted_full_text -> rss_content -> rss_summary
```

The renderer records which source was used for each item. Missing full text is not an error for a
daily edition. Automatically scheduling extraction for every candidate is out of scope for the
first release.

## Durable state

### Jobs

The v0.3 design may add SQLite lease-based jobs for:

```text
feed_fetch
article_translate
edition_prepare
edition_editorial
edition_render
delivery_send
```

Explicit `article_extract` jobs may be created by an operator or Agent request, but are not created
for every daily candidate. Jobs have an idempotency key, priority, deadline, status, attempts,
`next_attempt_at`, lease owner/expiry, safe error code, and aggregate usage fields. Expired leases
are recoverable after process restart.

### Edition runs

Suggested lifecycle:

```text
planned -> refreshing -> selecting -> frozen -> editorial -> rendered -> queued
                                                             \-> degraded
queued -> delivering -> delivered
                  \-> retry_wait -> delivering
                  \-> terminal
```

An edition is uniquely identified by topic, local edition date, and profile version. Repeated timer
activation must resume or observe the same edition, not create duplicate content.

### Delivery outbox

Each outbox item includes:

- edition ID, channel, and opaque target reference;
- idempotency key;
- payload/artifact hash, not a copied secret;
- attempt count and `next_attempt_at`;
- provider response ID when available;
- delivered timestamp or safe terminal error code.

A delivery result distinguishes content generation failure, editorial degradation, transient send
failure, terminal send failure, and confirmed delivery.

## Feishu custom app boundary

The outbound adapter uses a Feishu custom app identity and the official message API. Credentials are
injected through the existing root-owned systemd credential mechanism and are never stored in TOML,
SQLite payloads, logs, reports, Git, or Pi sessions.

Initial outbound content consists of:

1. a compact Feishu message/card with topic, date, highlights, item count, and degraded status;
2. the complete Markdown edition as an uploaded artifact or a link managed by the adapter.

Automatic creation of native Feishu documents is deferred until card-plus-artifact delivery is
stable and its additional permissions are reviewed.

Inbound interaction is a separate component. It must:

- validate Feishu event authenticity and encryption configuration where enabled;
- deduplicate event IDs before invoking Pi;
- enforce tenant, chat, and user allowlists;
- reject or request confirmation for non-allowlisted actions;
- convert messages into typed operations rather than placing raw event payloads in a shell;
- redact credentials, private headers, and unnecessary message metadata from Pi input.

Exact Feishu permission names, event mode, and target identifier type are verified against the
production tenant during implementation. The adapter exposes project-defined error codes rather
than leaking complete Feishu responses.

Official references:

- [Send messages](https://open.feishu.cn/document/server-docs/im-v1/message/create)
- [Feishu cards with app bots](https://open.feishu.cn/document/feishu-cards/quick-start/send-feishu-cards-with-app-bots)
- [Event subscription mode](https://open.feishu.cn/document/event-subscription-guide/event-subscriptions/event-subscription-configure-/choose-a-subscription-mode/send-notifications-to-developers-server)

## Agent-safe operation contracts

The first typed JSON operations are expected to cover:

```text
feed probe/add/update/disable/list/health
topic show/update
pipeline status
edition status/rebuild/redeliver
article extract
```

Mutation responses include schema version, operation ID, actor/source, changed object ID, result,
and safe warnings. Mutation audit records store identifiers and aggregate facts only, never article
bodies, private feed URLs with query values, authorization headers, secrets, or full provider
responses.

Operations requiring explicit confirmation include:

- private or authenticated feed configuration;
- unknown policy exceptions or unsafe redirects;
- bulk extraction/translation above the normal bounded request;
- budget increases or mode changes to a less restrictive policy;
- destructive retention, vacuum, restore, or data deletion;
- Feishu target or authorization-scope changes.

## Cost and rate-control framework

Budget modes are:

```text
observe -> warn -> enforce
```

Initial production operation uses `observe`, but always enforces non-financial disaster ceilings
such as maximum candidates, characters, request concurrency, and Pi context size.

Usage is aggregated by UTC event time and an `Asia/Shanghai` billing/reporting date for:

- feed host requests, response bytes, 403/429/timeouts, and fetcher type;
- translation provider requests, source characters, retries, provider/model, and estimated cost
  when a rate is configured;
- Pi provider/model calls, input/output tokens, retries, and estimated cost when available;
- Feishu sends, retries, 429s, and final delivery status.

The framework accepts nullable soft/hard daily and monthly limits so concrete values can be added
without changing schemas or command contracts. A hard-limit breach pauses costly work and selects a
configured degradation path; it must not start an unlimited retry loop.

## Reliability and anti-bot policy

- Continue using ETag/Last-Modified, HTTPS-only redirect checks, bounded responses, optional curl,
  and secret headers from environment credentials.
- Add host-level concurrency/rate control, `Retry-After` handling, exponential backoff with jitter,
  and circuit-breaker state before increasing parallelism.
- Quarantine feeds that repeatedly return anti-bot placeholders, 403s, invalid XML, or terminal
  policy errors. The Agent may explain and suggest an official feed/API or stable replacement, but
  must not bypass CAPTCHA or access controls.
- A failed feed never prevents other feeds or a degraded edition from completing.

## Stable observability contracts

Extend versioned JSON contracts additively or introduce a new schema version for breaking changes.
Expose at least:

- per-topic next deadline and latest edition state;
- frozen candidate count, translated count, degraded reason, and rendered artifact status;
- pending/retrying/terminal jobs grouped by type and safe error code;
- pending/retrying/terminal delivery items and latest confirmed delivery;
- daily/monthly provider, Pi, and delivery usage aggregates;
- feed circuit-breaker/quarantine totals without article content or secrets.

## Delivery slices

1. **Contracts and schema design** — topic, edition, outbox, usage, migration, and rollback plan.
2. **Deterministic edition builder** — dynamic selection, provenance, empty/degraded rendering.
3. **Feishu outbound and outbox** — card/artifact delivery, retries, idempotency, test adapter.
4. **Deadline coordinator** — explicit timezone, restart recovery, cutoff and fallback behavior.
5. **Cost observation** — provider/Agent/delivery usage and safety ceilings.
6. **Agent-safe control plane** — feed/topic/edition typed operations and mutation audit.
7. **Pi editorial integration** — bounded structured input/output and deterministic fallback.
8. **Feishu inbound gateway** — event verification, allowlists, confirmation flow, operation routing.
9. **Durable worker isolation** — lease jobs and provider/host rate controls where operational tests
   demonstrate the synchronous path cannot meet the deadline.

Each schema-changing slice requires a WAL-aware pre-migration snapshot, migration test, verified
restore test, and documented rollback consequence. `main` must remain releasable; unfinished schema
or worker behavior cannot be merged behind an implicit runtime assumption.

## Acceptance criteria

### Deadline and degradation

- With an injected `Asia/Shanghai` clock, a scheduled topic produces at most one edition for a local
  date and reaches delivery or a recorded terminal state.
- If Pi is unavailable or exceeds its cutoff, a deterministic degraded edition is queued without
  waiting until the final deadline.
- Zero qualifying articles produces a successful, deliverable empty edition.
- A failed feed or translation provider cannot prevent unrelated work from reaching fallback.

### Content

- Selection is dynamic but all configured safety ceilings are enforced.
- Each rendered item reports whether it used extracted full text, RSS content, or RSS summary.
- Daily generation performs no implicit full-text extraction.
- Explicit selected-article extraction remains bounded, resumable, and independently reportable.

### Feishu delivery

- Repeated worker/timer execution does not duplicate a successfully delivered edition.
- Transient Feishu failures retry with bounded backoff; terminal failures retain a safe error code.
- Delivery evidence distinguishes queued, retried, terminal, and confirmed-delivered outcomes.
- Credentials and complete provider responses never appear in logs, reports, SQLite payloads, Git,
  or Pi prompts.

### Agent operations

- Pi can use typed operations to probe/add a public feed, inspect status, request selected full-text
  extraction, and inspect/retry an edition without arbitrary shell or raw database access.
- Inbound Feishu events are authenticated, deduplicated, and allowlisted before Pi invocation.
- Sensitive, high-cost, permission-changing, and destructive operations require explicit
  confirmation.
- Mutation audit records are sufficient to identify actor, operation, target, and outcome without
  storing sensitive content.

### Cost and operations

- Observe mode records feed, translation, Pi, and Feishu usage even when financial prices are unset.
- Safety ceilings remain active in observe mode.
- Adding warn/enforce thresholds requires configuration only, not a schema or API redesign.
- Upgrade, crash/lease recovery, outbox replay, backup/restore, and rollback drills pass.
- Lockfile, lint, tests, dependency audit, encoding, and diff checks pass.

## Out of scope for the first production slice

- multi-host workers, Redis/Celery, or replacing SQLite;
- automatic extraction for all daily candidates;
- bypassing access controls, CAPTCHA, or website terms;
- a fixed article quota per topic;
- hard-coded financial limits before usage observation;
- native Feishu document creation before card/artifact delivery is stable;
- autonomous destructive maintenance or unapproved credential/permission changes.

## Relationship to the v0.2 observation decision

The approved requirement for automatic deadline delivery is direct product evidence for designing
v0.3. The v0.2 observation window remains necessary to size polling intervals, provider limits,
worker concurrency, retention, and financial thresholds. Product approval opens design and bounded
vertical-slice work; it does not justify guessing production limits or skipping migration and
restore evidence.
