# v0.2 Slice 2: Durable manual batch checkpoints and resume

**Status:** Proposed for `feature/v0.2-batch-checkpoints`  
**Target version:** v0.2.0  
**Depends on:** v0.2 batch-accounting commits `cb13c03..2dfbde3`

## Goal

Allow an explicit `translate` or `extract` command interrupted by budget exhaustion, process
termination, or provider failure to resume its remaining selected articles without reprocessing
articles already completed successfully in that batch.

## Non-goals

- Replacing persisted translation retry state or feed synchronization.
- Asynchronous worker/job scheduling, automatic extraction, distributed claims, or provider
  circuit breakers.
- Replaying an arbitrary old CLI command after config/source data has changed.

## Schema

Migration 4 adds two tables:

```sql
CREATE TABLE batch_runs (
  id INTEGER PRIMARY KEY,
  command TEXT NOT NULL CHECK(command IN ('translate', 'extract')),
  selector_json TEXT NOT NULL,
  limits_json TEXT NOT NULL,
  status TEXT NOT NULL CHECK(status IN ('running', 'interrupted', 'succeeded', 'failed')),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  completed_at TEXT
);

CREATE TABLE batch_run_items (
  batch_run_id INTEGER NOT NULL REFERENCES batch_runs(id) ON DELETE CASCADE,
  article_id INTEGER NOT NULL REFERENCES articles(id) ON DELETE CASCADE,
  position INTEGER NOT NULL,
  status TEXT NOT NULL CHECK(status IN ('pending', 'succeeded', 'failed', 'skipped')),
  error_code TEXT,
  updated_at TEXT NOT NULL,
  PRIMARY KEY(batch_run_id, article_id),
  UNIQUE(batch_run_id, position)
);
```

Indexes support resume selection by `(batch_run_id, status, position)`. `selector_json` is
operator audit data, not SQL input. The selected article IDs are materialized immediately into
`batch_run_items`; resume never reruns the original selector, so later source/feed changes cannot
expand the batch.

## CLI semantics

New shared options:

```text
--checkpoint / --no-checkpoint     default: checkpoint for execution, no persistence for dry-run
--resume RUN_ID                    mutually exclusive with all selectors
```

A new execution creates a `batch_runs` row and ordered pending item rows before its first provider
request. Its JSON report includes `batch_run_id`.

`--resume RUN_ID` validates the command type and loads only pending/failed item rows in stored
order. It does not rerun succeeded rows. `failed` rows are retried because an operator explicitly
asked to resume. `skipped` rows are retried only when their prior reason was
`provider_budget_exhausted`; other skips remain terminal for that run.

Status transitions:

- `running`: batch is being executed;
- `interrupted`: budget exhaustion, signal, or unexpected command termination after a checkpoint;
- `failed`: an unrecoverable command-level configuration/report error;
- `succeeded`: no retryable batch items remain;
- a per-item provider failure remains `failed` while the run can finish as `succeeded` only if the
  command intentionally processed every selected item; the report distinguishes completed/failed.

For this slice, a run with any per-item failure ends `failed`; successful resume can later change
it to `succeeded` once no failed/pending items remain.

## Safety and migration

- Creating a checkpoint is one local SQLite transaction before external requests.
- Marking each item occurs after its persisted translation/extraction result is written.
- A process crash leaves pending items and `running`; `--resume` changes it to `interrupted` and
  continues them. There is no automatic resumption.
- Migration 4 requires the existing verified pre-migration SQLite snapshot and WAL test.
- Deleting articles cascades batch items; run audit metadata remains only while it has items.

## Test plan

1. Migration from schema 3 preserves data and creates indexes.
2. Creating a run materializes the exact ordered article ID set.
3. A budget interruption marks completed rows succeeded and remaining rows skipped/pending as
   appropriate; resume processes only remaining rows.
4. Resume rejects a run of the wrong command type and unknown run ID.
5. Source/feed changes after creation do not modify the stored selection.
6. A restored database retains batch runs/items and can resume.
