# v0.2 Operational Observation Protocol

## Purpose

Collect evidence after v0.2.0 before deciding whether RSS-Zen needs the v0.3 durable
worker/job-queue architecture. This protocol does not change service behavior and does not make
external feed/provider requests.

## Preconditions

- Observe only an approved deployment running the release tag `v0.2.0` or a documented security
  patch based on it.
- Use the configured production account and config path; do not copy secrets, headers, article
  bodies, provider responses, or private feed URLs into reports.
- Verify the release first:

  ```bash
  rss-zen --version  # when packaging exposes it
  git describe --tags --exact-match HEAD
  ```

- Never run `retention apply`, `maintenance vacuum`, a feed sync, or a provider command as part of
  observation unless separately approved by an operator.

## Observation window

Collect evidence for at least **14 calendar days** or at least **20 normal batch runs**, whichever
is longer. Record all timestamps in UTC.

At least once per day, collect only local health data:

```bash
sudo -u rss-zen /opt/rss-zen/current/.venv/bin/rss-zen status --json \
  --config /etc/rss-zen/rss-zen.toml > /var/lib/rss-zen/observations/status-UTC.json

sudo -u rss-zen /opt/rss-zen/current/.venv/bin/rss-zen doctor --json \
  --config /etc/rss-zen/rss-zen.toml > /var/lib/rss-zen/observations/doctor-UTC.json
```

If healthcheck timer is enabled, additionally record relevant journal metadata only:

```bash
sudo systemctl status rss-zen-healthcheck.timer --no-pager
sudo journalctl -u rss-zen-healthcheck.service --since '24 hours ago' --no-pager
```

Store raw JSON on the production host or in the Git-ignored local project-management report
location. Do not commit it.

## Required metrics

| Metric | Source | Why it matters |
|---|---|---|
| Feed stale / never-succeeded counts | `status --json` | Detects whether sequential work delays polling. |
| Pending, failed, terminal translations | `status --json` | Detects sustained processing debt. |
| Interrupted batches / resumable items | `status --json` | Measures manual resume burden. |
| Batch reports: selected/completed/failed/skipped, requests, characters | `--report-json` artifacts | Measures batch cost, failure and recovery patterns. |
| Provider 429/timeout error-code counts | `status --json` errors | Shows whether provider scheduling/rate limits are needed. |
| Database/WAL size, disk free bytes, backup age | `status --json`, `doctor --json` | Detects storage and maintenance pressure. |
| Healthcheck failures | systemd/journald | Detects deployment-level health issues. |

## Manual batch evidence

For operator-approved normal work, retain the generated run report locally:

```bash
rss-zen translate --status failed --report-json /var/lib/rss-zen/observations/translate-UTC.json \
  --config /etc/rss-zen/rss-zen.toml
```

Record whether `--resume` was required, but do not include article titles or source URLs in the
summary. Report aggregate counts and error codes only.

## v0.3 go/no-go thresholds

Open a v0.3 design task only if one or more thresholds persist across the observation window:

1. **Polling latency:** a normal sync/translation cycle exceeds half of the shortest configured
   poll interval, or stale feeds increase while feeds are otherwise reachable.
2. **Manual recovery burden:** operators need `--resume` at least three times per week, or
   resumable item count grows for seven consecutive days.
3. **Provider pressure:** 429, timeout, or retryable network failures exceed 5% of provider
   requests across at least two observation periods.
4. **Processing debt:** pending/failed translation counts grow for seven days despite normal
   operator batches.
5. **Explicit product requirement:** approved requirement for automatic background translation
   after ingestion that cannot be met by bounded manual batches.

If no threshold is met, keep the single-host synchronous model and continue maintenance through
v0.2 health/retention tooling.

## Decision record

At the end of the window, create a local project-management decision containing:

- observation start/end dates and release version;
- aggregate metrics and threshold results;
- go/no-go result for v0.3;
- any new risks or required operational fixes;
- references to local report filenames, never raw sensitive content.
